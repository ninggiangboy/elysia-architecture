# @mod/__name__

A business module of the kit, generated by `bun run gen:module __name__`. It answers `GET /api/__name__/ping` for signed-in
users and is the smallest thing that still has every layer: a domain object, a use case with a test, a Postgres schema with
its outbox and inbox, a route, a config slice, a manifest and an `install(host)`.

## Install

```bash
bun add @mod/__name__
bun run kit:add __name__      # wires it into the app: catalog, container, routes
bun run db:migrate
```

## Layers

| Folder | What lives there |
|---|---|
| `src/domain` | Rules with no I/O (`Reply`). |
| `src/application` | Use cases and their ports (`Ping`). |
| `src/infrastructure` | Adapters: the Postgres schema (`__name__` schema, outbox, inbox). |
| `src/presentation` | The Elysia routes. |
| `src/contracts` | What other modules may rely on: event names and payloads. |

## Config

`__NAME___REPLY` — what `ping` answers (default `pong`). Generated into `.env.example` from `src/config.ts`.

## Extension points

Adapters (ports passed to the factory), the config slice, integrations other modules ship for it, and app-level handlers on
the events in `src/contracts`. Changing rules inside a use case is not an extension point: eject the module instead (copy the package into `modules/__name__`,
rename it `@app/__name__`, keep the schema name and `migrations/`).

## Guarantees and limits

Events are delivered at least once: handlers must be idempotent. Nothing here talks to another module except through
`@mod/identity/contracts`.
